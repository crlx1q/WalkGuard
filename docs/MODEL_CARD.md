# Стартовая модель WalkGuard

## Происхождение и целостность

- Семейство: TensorFlow EfficientDet-Lite0, detection metadata, версия 1.
- [Карточка издателя](https://www.kaggle.com/models/tensorflow/efficientdet/tfLite/lite0-detection-metadata/1).
- [Официальный файл TensorFlow](https://storage.googleapis.com/download.tensorflow.org/models/tflite/task_library/object_detection/android/lite-model_efficientdet_lite0_detection_metadata_1.tflite).
- [Официальный пример, использующий этот вариант](https://github.com/tensorflow/examples/blob/master/lite/examples/object_detection/raspberry_pi/setup.sh).
- Лицензия: Apache 2.0; указана также во встроенных metadata самого файла; текст включён в assets/licenses.
- Размер: **4 563 519 байт**; веса не изменены.
- SHA-256: `2e04c53bfeac0ac2a30c057c7e2a777594ce39baaac35a92f74fb1e8c4fc4e0b`.
- Расположение: `android/app/src/main/assets/models/efficientdet_lite0.tflite`.
- Метки извлечены из встроенного `labelmap.txt`, а не составлены вручную.

Это вариант с `TFLite_Detection_PostProcess`, а не другой одноимённый файл MediaPipe с сырыми тензорами якорей. Подмена файла без проверки контракта запрещена: приложение завершит запуск с ошибкой загрузки модели.

## Контракт, проверенный реальным CPU-инференсом

Вход: UINT8 `[1,320,320,3]`, RGB, значения 0–255, scale 0.0078125, zero point 127. Квантизованы веса и вычисления. Дополнительное деление входных байтов на 255 не требуется.

Выходы float32, по индексам:

| Индекс | Размерность | Содержимое |
|---|---|---|
| 0 | `[1,25,4]` | Нормированные ymin,xmin,ymax,xmax |
| 1 | `[1,25]` | Индексы классов, с нуля |
| 2 | `[1,25]` | Confidence |
| 3 | `[1]` | Количество обнаружений |

CameraX выдаёт RGBA. Приложение учитывает row/pixel stride, cropRect и rotationDegrees, затем поворачивает кадр и вписывает его с полями RGB(127,127,127) в квадрат 320×320 без искажения пропорций. Координаты результатов переводятся обратно в нормированный повёрнутый crop. Превью использует тот же кадр; второго потока камеры нет.

Один Interpreter, два CPU-потока, один последовательный executor. GPU/NNAPI/облачные сервисы не используются. Runtime LiteRT встроен в APK; Google Play Services для инференса не нужны.

## Классы и ограничения

COCO 2017: 80 классов, 90 индексов с пропусками `???`. Полный список лежит рядом с моделью в `labels.txt`.

RiskEvaluator учитывает только: person, bicycle, car, motorcycle, bus, train, truck, bench, dog, cat, horse, cow, sheep, suitcase, chair, potted plant. Обнаружение остальных классов отражается в диагностике и не запускает предупреждение.

**Нет поддержки** ям, открытых люков, бордюров, ступеней, краёв дороги, ограждений, разметки и переходов. Модель не оценивает свободный путь, разрешение перехода дороги, точное расстояние или реальную скорость объекта. Наличие автомобиля не означает его приближение.

Факторы ошибок: темнота, блики, закрытый объектив, размытие, небольшой объект, необычный ракурс, неверное положение телефона. Эвристика наклона не умеет доказать видимость дороги.

## Фактически выполненная проверка

`docs/verification/model-smoke.json` содержит результаты четырёх реальных запусков LiteRT на Linux ARM64 CPU. Использовано [тестовое изображение TensorFlow Grace Hopper](https://storage.googleapis.com/download.tensorflow.org/example_images/grace_hopper.jpg); обнаружен `person`. Изображение в проект не включено.

Это только проверка загрузки, совместимости тензоров и выполнения модели. Время Linux-компьютера **не является** производительностью Android-устройства. Этот тест не измеряет полноту распознавания препятствий и не валидирует оценку риска.

Повторение с собственным контролируемым кадром:

```sh
python -m pip install ai-edge-litert numpy pillow
python tools/verify_model.py --image /path/to/scene.jpg --output result.json
```

## Следующий этап обучения

Для бордюров, ям, люков, краёв дороги и ступеней нужен отдельный размеченный датасет с изображениями именно с пешеходного телефона. Следует охватить высоту и наклон телефона, разные камеры, погоду, освещение, покрытия, перекрытия и отрицательные примеры. Кадры одной прогулки и одного места не должны попадать одновременно в train и test.

Нужны согласованные определения классов и опасных областей, проверка разметки, обучение детектора или сегментации, INT8-калибровка на репрезентативных данных и независимая проверка после квантизации. Измерять следует recall по классам и условиям, false negatives, ложные тревоги в минуту, задержку предупреждения, энергопотребление и нагрев на разных Android-устройствах. Для ступеней и краёв могут потребоваться сегментация, temporal-модель и данные глубины.

Пороги RiskEvaluator потребуется калибровать на отдельном наборе последовательностей. Начинать следует с записанных материалов и контролируемых сцен; проверка в дорожном движении не должна требовать от человека отвлекаться или полагаться на приложение.
